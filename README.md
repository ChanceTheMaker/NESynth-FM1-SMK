# NESynth — NES on FM-1 / SMK37

Shared InfoNES core for a local browser player and dual-core FM-1/SMK37 firmware. Supports **NTSC, mapper 0 (NROM), 1 (MMC1), 2 (UxROM), 3 (CNROM), 4 (MMC3), 9 (MMC2) and 11 (Color Dreams), one controller**. Includes From Below, CodeMaster, Diamond Chase, and an original diagnostic generated by `tools/diagnostic.py`. Homebrew licenses and pinned sources are in `web/homebrew/` and the website credits; no commercial ROMs are included.

The prototype fits the existing FM-1 memory map. The website plays NES/ZIP cartridges, browses a user-selected ROM folder, simulates FM-1 and SMK37 controls, builds cartridge firmware locally, and installs or restores FM-1 and SMK-37 Pro/Elite firmware over USB MIDI. **FM-1 picture, controls, both cores, and update/restart have been exercised. Punch-Out reached approximately 60 emulated frames/sec with audio-prioritized adaptive drawing; screen refresh is lower and other games remain experimental. SMK-37 Pro/Elite installers are experimental candidates; physical installation and playback validation remain pending.**

Live site: **https://chancethemaker.github.io/NESynth-FM1-SMK/**

## Bluetooth game loading (SMK-37 Pro, branch build 966)

**Hardware verified on the owner's SMK-37 Pro (2026-10-16):** The same 40,976-byte Super Mario Bros. cartridge transferred over BLE in **8.95 and 10.99 seconds**, down from 62.2 seconds on SMK965, with zero retries. These CLI timings include connection and verification, excluding discovery and the subsequent install/restart; data writes took 5.09 and 6.31 seconds. Both fresh connections passed, including reopening loading from gameplay. The installed length/CRC matched after restart, and gameplay ran at 59.9 emulated frames/sec with CPU1 active, no new audio underruns and no display timeouts. See `experiments/bluetooth/smk966-hardware.json` for scope and remaining checks.

SMK966 combines the NES player with a Bluetooth cartridge loader. Hold **PLAY + REC** for two seconds to open loading, open `web/bluetooth.html` in Chrome or Edge through a localhost web server, connect **NESynth SMK**, and drop a `.nes` or `.zip` game. **Send and play** transfers and verifies it, restarts the SMK to install it with the radio off, and boots the game. Fader 1 and the existing GameDude-style game controls are retained. Bluetooth closes during gameplay. One cartridge up to **262,672 bytes** is stored persistently; save RAM remains volatile. USB firmware replacement clears that cartridge slot.

```powershell
python tools/build_bluetooth_probe.py --loader
node tools/package_bluetooth_loader.mjs
python -m http.server 8766 --bind 127.0.0.1 --directory web
# Open http://127.0.0.1:8766/bluetooth.html
```

The build requires the pinned local Hortator/AC79 dependencies described below. This owner's unit also needs the already-verified private calibration backup options; `--loader` accepts the same `--private-calibration-backups` and `--private-unit-backups` pairs as the diagnostic. These local artifacts stay under ignored `build/bluetooth-loader/`; **PRIVATE firmware must not be published**. The generated `.fwsc`/`.smkupdate` are separate from the public SMK963 website installer.

SMK966 sends bounded bursts of eight packets, checks cumulative device progress, and replays missing data with a strict retry limit. Control messages still require acknowledgments, and the complete cartridge CRC is verified before installation. The controller enables 251-byte Data Length Extension and requests a 15-30 ms connection with zero peripheral latency; older peers can retain smaller packets. Tuning starts only after the application characteristic is accessed, allowing Windows service discovery to finish first. The browser automatically retains acknowledged writes for older SMK965 firmware. The pinned SDK files stay unchanged: only the generated controller configuration is adapted and its hash is recorded in the build report.

For local verification, `tools/upload_bluetooth_game.py GAME.zip` sends the game over Bluetooth, and `tools/inspect_bluetooth_loader.py` checks the installed cartridge's length/CRC over USB. `--open-loader` enters loading from the player. A successful transfer ACK is followed by separate persistent-storage and gameplay checks. The browser uploader preserves the existing bounded ZIP extraction and exact legacy-header repairs.

The loader reuses inactive gameplay RAM, verifies the entire cartridge, then resets the controller before touching flash. After reset it checks the retained cartridge again; failed retention leaves the old game untouched. Writes are confined to `0x5b000..0x9cfff`, read back, and published through metadata written last. Boot code, VM/music storage and the factory region are outside this range. USB recovery from an active radio resets directly into the RAM updater. The build checks code/slot boundaries and RAM-only flash reach; tests inject every flash I/O interruption and readback corruption.

## Try it

```powershell
python tools/build.py web
python tools/serve.py --port 8816
```

Open <http://127.0.0.1:8816/>. The diagnostic starts silently. Loading a cartridge, pressing a game control, or choosing **Enable sound** starts audio. **Audio on** confirms the browser audio context is running; a suspended context can be enabled again. Move the diamond with arrows/WASD; A changes pitch and B changes background color. Enter/X = A, Space/Z = B, P = Start, Shift = Select. On-screen controls also work. Input taps are held at least 40 ms; focus loss releases all controls.

Drop a `.nes` or `.zip` file onto **Drop your game here** in step 1, or click the same area to choose one. This single picker feeds both the browser player and installer. Load one file at a time. ZIPs containing one `.nes` file open automatically; archives containing several show a cartridge picker. Standard stored and DEFLATE ZIPs are supported, including cartridges in subfolders and uppercase `.NES` extensions. Mac metadata files are ignored. Extraction and checksum validation happen locally; nothing is uploaded. The browser limits archives to 64 MiB and extracted cartridges to 1 MiB, and rejects encrypted, split, ZIP64, damaged, or unsupported-compression archives. DEFLATE extraction requires a browser with `DecompressionStream('deflate-raw')` support.

Legacy `DiskDude!` headers are repaired in memory when imported. The checksum-identified Ms. Pac-Man (Tengen) overdump also has its excess graphics removed and horizontal mirroring restored, using the verified PRG/CHR and board metadata in [MAME](https://github.com/mamedev/mame/blob/master/hash/nes.xml) (`mspacmnt`). Unknown oversized dumps are still rejected; this does not enable NES 2.0 or special consoles. The original NES/ZIP file is never rewritten. The browser player, firmware builder, and Python cartridge reader use the same repair.

Accepted cartridges have a standard iNES 1.0 header. Mapper 0 accepts 16/32 KiB PRG and zero/8 KiB CHR; mapper 9 accepts power-of-two PRG sizes from 32 to 128 KiB and CHR ROM from 8 to 128 KiB. Mapper 1 supports standard MMC1B boards with power-of-two 16?256 KiB PRG, zero/8?128 KiB CHR, and at most 8 KiB PRG RAM. Expanded SxROM RAM/512 KiB PRG boards and MMC1A variants are not supported. An optional 512-byte trainer is supported. NES 2.0, PAL, other mappers, special console variants, and unsupported RAM sizes are rejected before entering the core. ZIP support does not change cartridge compatibility. A valid header does not guarantee accurate gameplay.

Mapper 2 supports standard UxROM with 32–256 KiB PRG and 8 KiB CHR RAM. Mapper 3 supports CNROM with 16/32 KiB PRG and 8/16/32 KiB CHR ROM. Mapper 4 supports standard MMC3 banking with 32–512 KiB PRG, zero/8–256 KiB CHR, four-screen mirroring and PRG-RAM protection. Bank sizes must be powers of two. The browser can load larger MMC3 games than the instrument: device firmware reserves 524,816 bytes (512 KiB plus header and trainer). Oversized device games get a separate error and remain playable in the browser. UxROM/CNROM use conflict-free register writes; MMC3 IRQs are a scanline approximation, with MMC3A/MMC6 and clone-specific behavior unimplemented. These are experimental compatibility limits, not a guarantee for every game.

The browser's default game simulator is a CRT television with a console and playable controller beneath it. The NESynth logo is on its gray enclosure. Instrument simulators retain the GameDude key/pad/PLAY/RECORD mappings. Drag the TV channel readout or upper tuning knob to discover 12 animated demoscene channels (04–15). Channel 03 or Escape returns to the loaded game without replacing it; emulation and its audio stop while a demo is showing. Click the left/right halves of either TV dial to lower/raise its setting; dragging still works. The lower TV volume knob and browser volume slider stay in sync. Fullscreen opens a movable retro clicker with channel and volume buttons, a CH 03 game button, and a close button. Reopen it with TV remote. Channel and volume controls also support arrow keys, Home and End.

FM-1_960 adds these three mappers and the larger cartridge slot. The application occupies 569,800 of 581,564 bytes with the original diagnostic embedded. Native, WASM, sanitizer, bank/IRQ/RAM protection, package round-trip and forward/reverse loader tests pass. User-supplied TetrisT, Super Pitfall, Super Shinobi and Super C ZIPs ran 3,600 frames with audio and inspected pictures; the two MMC3 games also passed full-versus-adaptive rendering/audio comparisons. These local games are not distributed. Physical validation of this new build remains pending.

FM-1_961 additionally supports mapper 11 (Color Dreams): power-of-two 32–128 KiB PRG and 8–128 KiB CHR ROM. A checksum-specific import repair clears only reserved header bytes 11–15 in the reported Simpsons dump; unknown payloads remain rejected. Simpsons and Shockwave each completed a 3,600-frame local playback run with audio and firmware packing. Simpsons still shows lower-screen rendering corruption; accepting its header does not establish accurate gameplay. The SMK source now includes a bounded RAM-only USB updater and compiles with the 512 KiB cartridge slot; the SMK browser installer is now available as the experimental SMK-37_963 candidate described below.

Battery RAM persists in browser storage, keyed by cartridge SHA-256, with `.sav` import/export. Only cartridges with the battery flag expose saves. Device save RAM remains volatile. A reset preserves battery RAM; loading a cartridge starts a fresh core session before browser save restoration.

## Build and verify

Requires Python 3, Node, and Zig. Instrument compilation uses WSL and the JieLi pi32v2 toolchain. Defaults match the local GameDude setup; override with `ZIG`, `JIELI_TOOLCHAIN`, `--zig`, or `--toolchain`.

```powershell
npm test
python tools/build.py sanitize
python tools/build.py fm1
python tools/build.py smk37
```

`sanitize` requires g++ in WSL. It runs the host suite with AddressSanitizer and UndefinedBehaviorSanitizer. Normal builds use no downloaded packages and do not access any connected device.

Run `npm run firmware` to regenerate the verified browser template (requires the local pinned AC79 SDK and restore fixture configured in `tools/package_fm1.py`). The template contains only our original diagnostic.

Hardware outputs are under `build/fm1/` and `build/smk37/`, with ELF symbols, section reports, manifests, and `nes-NOT-FOR-INSTALL.bin`. These are raw link products, **not `.fwsc` packages**. `tools/package_fm1.py` creates and validates `.fwsc` packages with forward/reverse loader simulations. The experimental source identity is `FM-1_961`. Do not feed raw link binaries to an updater.

`--rom path.nes` or `--rom path.zip` embeds a private cartridge. For a ZIP containing several cartridges, add `--rom-entry "folder/game.nes"`. `--rom-capacity` changes the reserved file slot. Build artifacts are ignored. The default 64 KiB slot accommodates NROM; MMC2 cartridges may need a larger slot (for example, `--rom-capacity 262672`). Enlarging it does not enable more mappers.

## Architecture

- CPU0 owns NES CPU/PPU/APU emulation, controller state, audio interrupts, USB, and LCD DMA.
- Rendering uses a 256-word scratch scanline, then a 61,440-byte indexed frame.
- CPU1 scales an immutable indexed-frame snapshot into a 240×225 RGB565 buffer. The image is centered at LCD y=7; both axes use a 15/16 scale.
- Hardware adaptively rasterizes every third to sixth emulated frame, targeting 10?20 pictures/sec while running CPU/APU and mapper fetches on every frame. Drawing backs off when the audio queue falls below 2,200 samples. The browser rasterizes every frame. CPU1 compares RGB565 rows against the last submitted image; LCD DMA transfers only the changed row range. Duplicate raster frames are not resubmitted. Worker timeout/fault retirement and local scaling fallback are retained, with a full refresh after a fault.
- MMC1/MMC2 decode only fetched tile rows and caches them by immutable CHR-ROM address. The row cache resets when a cartridge resets or loads. Hot CPU, PPU, mapper and scaler code runs from executable SRAM on the instruments.
- The 44.1 kHz mono ring feeds both output channels. Browser audio scheduling drives emulation while sound is active; a monotonic timer drives silent playback. The rational sample count targets approximately 60.0988 NTSC frames/sec.
- The original APU is an approximate linear mix with a DC-blocking filter. No claim of cycle-accurate PPU/APU timing, exact sprite behavior, emphasis-color emulation, or broad NROM compatibility is made.

The retained `gp_*` and some `gb_*` names are the GameDude platform interface, not a second Game Boy core.

## Website firmware workflow

The **Install on your instrument** panel sits beside the browser player (above it on small screens). Its four steps keep the selected game, connection status and final install action visible together.

1. **Choose your game:** drag a `.nes` or `.zip` onto **Drop your game here**, click that same area to choose a file, or select a free homebrew. This is the single cartridge picker for both browser playback and installation. Folder browsing and multi-game ZIP selection stay within this step; choosing a new file clears any previously prepared firmware.
2. **Connect your FM-1:** turn it on and connect it directly to the computer with a USB data cable. Disconnect the recovery adapter, close other MIDI apps and unplug other instruments. Factory M-VAVE V15 is supported. Use Chrome/Edge on HTTPS or localhost and allow MIDI/SysEx access.
3. **Prepare your game:** the browser patches and verifies a pinned template locally. Preparation does not write the device. Saving a `.fwsc` is optional; no download or compiler is needed to install from this page.
4. **Install and play:** the always-visible install button becomes available after preparation. It checks the device again, pauses emulation, locks cartridge changes and requires the expected restart identity before reporting success. Keep power and USB connected. Interrupted transfers offer log export and an explicit retry; no write is retried automatically.

Connection help, transfer details and **Return to the original M-VAVE synth** are expandable below the steps. Restoration verifies the included M-VAVE V15 image. Generic `ota-FM-1` loaders still require physical-model confirmation because some SMK loaders use that identity.

Run `npm run test:ui` with Playwright and Chrome available for isolated desktop/mobile UI checks. `PLAYWRIGHT_MODULE` may point to an existing Playwright module. These tests simulate MIDI and never access a device. SMK UI tests require the pinned stock fixtures at `build/smk37/stock-pro.fwsc` and `build/smk37/stock-elite.fwsc` (see the SMK section). The existing `npm run test:site` checks firmware packaging and transport behavior.

The FM-1/SMK-37 Pro/SMK-37 Elite simulator views use the shared key/pad mappings. Click highlighted controls or enlarge the live screen. The classic NES controller remains available. Choose the exact model in the installer separately. Changing models clears prepared firmware and requires a fresh connection check; it keeps the selected cartridge.

## SMK-37 Pro and Elite installer

Select **SMK-37 Pro** (or **SMK-37 Elite**) in the same four-step installer, drop a cartridge, then **Connect → Prepare → Install**. The candidate is **SMK-37_963**, with the same GameDude/Game Boy piano keys, pads, PLAY (Start) and RECORD (Select). Its 573,728-byte application fits the 581,564-byte budget, including the 524,816-byte cartridge slot and RAM updater. **Fader 1 controls game volume: down = mute, up = full.** Volume changes ramp over one audio block to avoid clicks. Until the first valid fader sample, output starts at the previous 25% level; an ADC failure holds the last volume. The owner has run SMK-37_962 on Pro hardware; read-only diagnostics confirmed CPU1 operation. Physical performance and controls with this new candidate still need validation, as do Elite hardware and recovery.

First installation accepts official M-VAVE **016** for the selected model. The browser downloads that model's pinned official package from the [SMK documentation mirror](https://github.com/jonathaslacerda/smk-37-pro-docs/tree/ab85d7340163ba9e171dc9396e31c034829bbc02/firmware), checks its exact SHA-256, and creates the cartridge package locally. The optional download is a wrapped `.fwsc`; the raw `smk37-template.bin` is not an installable file. Updater-enabled Felucca/Sloop/Melodee builds with SMK identity 922 or newer, Doom identity 007 or newer, and NESynth use the portable RAM-loader route. Older firmware without that updater requires adapter migration.

**Return to the original M-VAVE synth** restores the exact selected model's 016 application. The RAM updater checks the supported flash chip, factory boot CRC and per-device calibration before writing. It preflights all sectors, writes only `0x4000..0x9d000`, verifies each sector and preserves boot/calibration. It requires an explicit retry after interruption and an exact restart identity before success. Power loss during programming may require adapter recovery. Generic `ota-FM-1` identity is accepted for Elite only after explicit physical-model confirmation.

SMK-37_962 sends LCD pixel data asynchronously, allowing NES emulation and audio production to continue during DMA. The shared framebuffer remains reserved until completion; a 250 ms transfer timeout disables the display while leaving emulation and USB recovery available. LCD DMA is stopped before entering the RAM updater. CPU1 scaling, adaptive rendering and Fader 1 volume remain enabled. On the owner's Pro running Super Mario Bros. (JU), SMK-37_962 measured 41.96 emulated frames/sec, 88.20 new audio underruns/sec and no CPU1 faults/fallbacks or LCD timeouts. The scanner consumed 33.86% of elapsed CPU time and completed about 12,545 full scans/sec (about 200,718 interrupts/sec). LCD updates were 3.62/sec during this sample; unchanged rows/frames are omitted, so that value depends on scene motion.

SMK-37_963 addresses that measured scanner load by changing only SPI2's scan divider from 5 to 95, before the first transfer. The 16-row latch sequence, ADC settling/completion pipeline, keys, pads and Fader 1 mapping remain intact. Expected full keyboard scan rate is around 1 kHz; actual input responsiveness, analog sweep rate and game speed require a new physical measurement. The vendored scanner now accepts `SMK37_SCAN_BAUD`, retaining its original default of 5; NESynth's local configuration supplies 95. This does not change CPU, audio or LCD clocks.

Build the diagnostic-only template with `python tools/public_smk_template.py`. Download the two files from the pinned URLs in `web/vendor/smk37-stock.js` to the ignored `build/smk37/stock-pro.fwsc` and `stock-elite.fwsc`, then run:

```powershell
npm run test:smk -- build/smk37/stock-pro.fwsc build/smk37/stock-elite.fwsc
npm run test:ui
```

The checks cover exact ROM packing, both model wrappers, immutable update data, official/custom/active-loader handoffs, interrupted transfers, incorrect restart rejection, factory restore and the single browser installer. The C updater simulation also consumes each actual generated application packet with a clearly synthetic calibration fixture, exercising flash limits and readback. CI runs these package and loader checks before publishing. Synthetic fixtures are not device backups or hardware validation.

Updater sources and browser packaging are adapted from [Doom's SMK updater](https://github.com/ChanceTheMaker/doom-fm1-smk/tree/44315112d4a9855070488ea1b45604ec56491e3e), retaining the Felucca/Sloop credits and GPL notices. ## Remaining hardware work

The `feat/bluetooth-game-loader` branch investigates a resident game loader and
wireless cartridge uploads. [Reconciliation evidence](experiments/bluetooth/reconciliation.json)
compares DEADACTIVE's [Hortator Bluetooth implementation](https://github.com/deadactive/hortator/tree/7e3415971c5800b4a3ad0146a7d95615883d7d96/firmware/src/ble)
with the existing Felucca peripheral diagnostics. Hortator's five Bluetooth host
test groups and startup-check self-test pass locally. Its cooperative scheduler
and stored-calibration approach are useful references; its central MIDI role is
different from a phone-facing cartridge receiver. That initial branch did not
enable a Bluetooth runtime. The follow-up diagnostic is described below; reliable
file transfer and device performance remain open. The published SMK963 build
remains unchanged. The owner reports substantially improved SMK963 playback;
post-change FPS and complete control validation have not been measured.

The follow-up **`feat/bluetooth-loader-prototype`** branch contains a non-installable
target link probe and a bounded cartridge receiver. [Measured fit evidence](experiments/bluetooth/prototype-fit.json)
records the real NESynth + pinned Hortator central stack + receiver link:

| Cartridge allocation | Application bytes | Free application bytes |
| --- | ---: | ---: |
| 256 KiB + 528-byte header/trainer allowance | 439,264 | 142,300 |
| 384 KiB + 528-byte header/trainer allowance | 570,336 | 11,228 |

Both use 56,288 of 73,728 bytes of regular RAM and 361,952 of 368,640 bytes
of buffer/CPU1-stack RAM. Bluetooth's heap and cooperative task records share
the inactive 61,440-byte `video_source` buffer. This measures the storage layout;
it does **not** implement the required gameplay/loader ownership transition.
Gameplay and Bluetooth must never use this buffer together. A future loader
must quiesce CPU1, display DMA and emulation before radio startup, then use
verified teardown or a reboot before gameplay. The 256 KiB option leaves more
space for that integration; the 384 KiB result is not a promised final capacity.
The existing 512 KiB public template is unchanged.

The receiver has BEGIN/DATA/COMMIT/ABORT operations, 512-byte chunks, bounded
relative offsets, chunk and full-image CRCs, exact duplicate acknowledgment,
and a publish gate after readback and backend ROM validation. Host tests exercise
corruption, gaps, retries, interruption and backend failures under ASan/UBSan.
There is no physical flash backend, cartridge wire protocol adapter or frontend
yet. The separate diagnostic GATT service below only echoes RAM data. The callback
backend must invalidate staging before writes and
publish only a fully validated image; power-loss recovery needs separate hardware
implementation and tests. No old-game preservation is implied.

`tools/inspect_ble_calibration.py` only reads private full-flash backups and
prints candidate offsets/counts. Two byte-identical stock reads from the owner's
SMK Pro contain two distinct checksum-valid VM item 187 candidates. Record
selection was initially unverified; the follow-up below resolves the candidate
under the pinned SDK's bank rules. Radio acceptance still needs a device test. No private backup,
calibration payload or Bluetooth address is included in the repository.

The validated Pro016 flash directory places VM at `0x9d000` with length `0x23000`.
The pinned SDK `cfg_tool.a` caps sector-aligned VM at 128 KiB and divides it into
two banks. The reader uses bank headers at `0x9d000` and `0xad000`, walks records
sequentially, checks every record CRC, and requires RF trim, crystal and PA data.
It refuses ambiguous/transitional banks, malformed records and failed reads;
it never runs SDK VM initialization, defrag or writes. On the owner's paired stock
backup it selects RF record `0x9d015` after validating 14 records. The second
candidate `0xbe015` is outside the SDK-managed range and is not used. This reader
targets the audited SMK Pro layout; it does not claim to handle every VM revision.

For this case only, `--diagnostic --private-calibration-backups FIRST SECOND`
accepts two identical full stock backups and validates their records with the
same C parser. It embeds only RF/crystal/PA records and the protected 8 KiB
factory region in an ignored local image. Before using the saved records, the
device must match the validated 556-byte `usrtrim` record at `0xc1000` byte for
byte, the same record the SMK updater and Melodee use as the unit fingerprint.

compared separately to report changed-sector offsets without exposing bytes. This does not restore or write VM/music storage. Packages are prefixed

published. This fallback is device-specific, available to the diagnostic and SMK965

Read-only diagnostic SysEx requests use `7D 4E 53 version` (`7D 'N' 'S'`), separate from GameDude. Version 3 appends five uint32 fields to the retained 35-field platform record: last/max/total emulator ticks, measured frame count, and maximum observed LCD completion time. Values use five 7-bit little-endian chunks; timer frequency is 24 MHz. Total ticks wrap at 32 bits. LCD time includes delayed CPU polling and therefore bounds observed completion latency, not exact wire time.

Version 4 retains those 40 fields and appends cumulative CPU, PPU, APU and scan-IRQ ticks. IRQ time overlaps the other measurements. `python tools/diagnose_device.py --samples 4 --interval 2` collects read-only measurements and computes frame rates and per-frame timings.
