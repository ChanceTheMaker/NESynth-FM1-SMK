# NESynth — NES on FM-1 / SMK37

Shared InfoNES core for a local browser player and dual-core FM-1/SMK37 firmware. Supports **NTSC, mapper 0 (NROM), 1 (MMC1), 2 (UxROM), 3 (CNROM), 4 (MMC3) and 9 (MMC2), one controller**. Includes From Below, CodeMaster, Diamond Chase, and an original diagnostic generated by `tools/diagnostic.py`. Homebrew licenses and pinned sources are in `web/homebrew/` and the website credits; no commercial ROMs are included.

The prototype fits the existing FM-1 memory map. The website plays NES/ZIP cartridges, browses a user-selected ROM folder, simulates FM-1 and SMK37 controls, builds cartridge firmware locally, and installs or restores FM-1 firmware over USB MIDI. **FM-1 picture, controls, both cores, and update/restart have been exercised. Punch-Out reached approximately 60 emulated frames/sec with audio-prioritized adaptive drawing; screen refresh is lower and other games remain experimental. SMK37 flashing remains disabled.**

Live site: **https://chancethemaker.github.io/NESynth-FM1-SMK/**

## Try it

```powershell
python tools/build.py web
python tools/serve.py --port 8816
```

Open <http://127.0.0.1:8816/>. The diagnostic starts silently. Loading a cartridge, pressing a game control, or choosing **Enable sound** starts audio. **Audio on** confirms the browser audio context is running; a suspended context can be enabled again. Move the diamond with arrows/WASD; A changes pitch and B changes background color. Enter/X = A, Space/Z = B, P = Start, Shift = Select. On-screen controls also work. Input taps are held at least 40 ms; focus loss releases all controls.

Drop a `.nes` or `.zip` file onto **Drop your game here** in step 1, or click the same area to choose one. This single picker feeds both the browser player and installer. Load one file at a time. ZIPs containing one `.nes` file open automatically; archives containing several show a cartridge picker. Standard stored and DEFLATE ZIPs are supported, including cartridges in subfolders and uppercase `.NES` extensions. Mac metadata files are ignored. Extraction and checksum validation happen locally; nothing is uploaded. The browser limits archives to 64 MiB and extracted cartridges to 1 MiB, and rejects encrypted, split, ZIP64, damaged, or unsupported-compression archives. DEFLATE extraction requires a browser with `DecompressionStream('deflate-raw')` support.

Legacy `DiskDude!` headers are repaired in memory when imported. The checksum-identified Ms. Pac-Man (Tengen) overdump also has its excess graphics removed and horizontal mirroring restored, using the verified PRG/CHR and board metadata in [MAME](https://github.com/mamedev/mame/blob/master/hash/nes.xml) (`mspacmnt`). Unknown oversized dumps are still rejected; this does not enable NES 2.0 or special consoles. The original NES/ZIP file is never rewritten. The browser player, firmware builder, and Python cartridge reader use the same repair.

Accepted cartridges have a standard iNES 1.0 header. Mapper 0 accepts 16/32 KiB PRG and zero/8 KiB CHR; mapper 9 accepts power-of-two PRG sizes from 32 to 128 KiB and CHR ROM from 8 to 128 KiB. Mapper 1 supports standard MMC1B boards with power-of-two 16?256 KiB PRG, zero/8?128 KiB CHR, and at most 8 KiB PRG RAM. Expanded SxROM RAM/512 KiB PRG boards and MMC1A variants are not supported. An optional 512-byte trainer is supported. NES 2.0, PAL, other mappers, special console variants, and unsupported RAM sizes are rejected before entering the core. ZIP support does not change cartridge compatibility. A valid header does not guarantee accurate gameplay.

Mapper 2 supports standard UxROM with 32–256 KiB PRG and 8 KiB CHR RAM. Mapper 3 supports CNROM with 16/32 KiB PRG and 8/16/32 KiB CHR ROM. Mapper 4 supports standard MMC3 banking with 32–512 KiB PRG, zero/8–256 KiB CHR, four-screen mirroring and PRG-RAM protection. Bank sizes must be powers of two. The browser can load larger MMC3 games than the instrument: device firmware reserves 524,816 bytes (512 KiB plus header and trainer). Oversized device games get a separate error and remain playable in the browser. UxROM/CNROM use conflict-free register writes; MMC3 IRQs are a scanline approximation, with MMC3A/MMC6 and clone-specific behavior unimplemented. These are experimental compatibility limits, not a guarantee for every game.

The browser's default game simulator is a CRT television with a console and playable controller beneath it. The NESynth logo is on its gray enclosure. Instrument simulators retain the GameDude key/pad/PLAY/RECORD mappings.

FM-1_960 adds these three mappers and the larger cartridge slot. The application occupies 569,800 of 581,564 bytes with the original diagnostic embedded. Native, WASM, sanitizer, bank/IRQ/RAM protection, package round-trip and forward/reverse loader tests pass. User-supplied TetrisT, Super Pitfall, Super Shinobi and Super C ZIPs ran 3,600 frames with audio and inspected pictures; the two MMC3 games also passed full-versus-adaptive rendering/audio comparisons. These local games are not distributed. Physical validation of this new build remains pending.

Battery RAM persists in browser storage, keyed by cartridge SHA-256, with `.sav` import/export. Only cartridges with the battery flag expose saves. Device save RAM remains volatile. A reset preserves battery RAM; loading a cartridge starts a fresh core session before browser save restoration.

## Build and verify

Requires Python 3, Node, and Zig. Instrument compilation uses WSL and the JieLi pi32v2 toolchain. Defaults match the local GameDude setup; override with `ZIG`, `JIELI_TOOLCHAIN`, `--zig`, or `--toolchain`.

```powershell
npm test
python tools/build.py sanitize
python tools/build.py fm1
python tools/build.py smk37
```

`sanitize` requires g++ in WSL. It runs the host suite with AddressSanitizer and UndefinedBehaviorSanitizer. Normal builds use no downloaded packages and do not access any connected device.

Run `npm run firmware` to regenerate the verified browser template (requires the local pinned AC79 SDK and restore fixture configured in `tools/package_fm1.py`). The template contains only our original diagnostic.

Hardware outputs are under `build/fm1/` and `build/smk37/`, with ELF symbols, section reports, manifests, and `nes-NOT-FOR-INSTALL.bin`. These are raw link products, **not `.fwsc` packages**. `tools/package_fm1.py` creates and validates `.fwsc` packages with forward/reverse loader simulations. The experimental source identity is `FM-1_960`. Do not feed raw link binaries to an updater.

`--rom path.nes` or `--rom path.zip` embeds a private cartridge. For a ZIP containing several cartridges, add `--rom-entry "folder/game.nes"`. `--rom-capacity` changes the reserved file slot. Build artifacts are ignored. The default 64 KiB slot accommodates NROM; MMC2 cartridges may need a larger slot (for example, `--rom-capacity 262672`). Enlarging it does not enable more mappers.

## Architecture

- CPU0 owns NES CPU/PPU/APU emulation, controller state, audio interrupts, USB, and LCD DMA.
- Rendering uses a 256-word scratch scanline, then a 61,440-byte indexed frame.
- CPU1 scales an immutable indexed-frame snapshot into a 240×225 RGB565 buffer. The image is centered at LCD y=7; both axes use a 15/16 scale.
- Hardware adaptively rasterizes every third to sixth emulated frame, targeting 10?20 pictures/sec while running CPU/APU and mapper fetches on every frame. Drawing backs off when the audio queue falls below 2,200 samples. The browser rasterizes every frame. CPU1 compares RGB565 rows against the last submitted image; LCD DMA transfers only the changed row range. Duplicate raster frames are not resubmitted. Worker timeout/fault retirement and local scaling fallback are retained, with a full refresh after a fault.
- MMC1/MMC2 decode only fetched tile rows and caches them by immutable CHR-ROM address. The row cache resets when a cartridge resets or loads. Hot CPU, PPU, mapper and scaler code runs from executable SRAM on the instruments.
- The 44.1 kHz mono ring feeds both output channels. Browser audio scheduling drives emulation while sound is active; a monotonic timer drives silent playback. The rational sample count targets approximately 60.0988 NTSC frames/sec.
- The original APU is an approximate linear mix with a DC-blocking filter. No claim of cycle-accurate PPU/APU timing, exact sprite behavior, emphasis-color emulation, or broad NROM compatibility is made.

The retained `gp_*` and some `gb_*` names are the GameDude platform interface, not a second Game Boy core.

- 256 seeded header mutations and 64 seeded random NROM programs in WebAssembly. This is limited robustness coverage, not an exhaustive security audit.
- Host diagnostic under address/undefined-behavior sanitizers.
- FM-1 and SMK37 cross-compilation, linker memory bounds, FM-1 USB updater symbol retention.
- Chrome visual preview, audio activation, keyboard movement, pause/resume.
- ZIP stored/DEFLATE extraction, streamed data descriptors, subfolders, multiple-cartridge selection, CRC verification, size bounds, malformed archives, and extracted-cartridge playback in WebAssembly; Python build-input extraction tests.
- MMC2 PRG/CHR bank selection, bounded register values, exact latch addresses, mirroring, reset, and post-fetch latch switching for background and sprite rendering.
- A user-provided Punch-Out ZIP ran 3,600 frames in WebAssembly with audio output, reaching the Glass Joe match. Screenshots were inspected; this is a limited smoke test, not a complete game or timing validation. `node tools/smoke_rom.mjs path.zip` repeats the local check without publishing cartridge data.

FM-1_957 (Punch-Out) measured 60.09 emulated frames/sec with zero new audio underruns during the last sample window. The underrun counter stayed at its post-startup value of 18 between uptime 30.6 and 363.3 seconds, including user gameplay. CPU1 remained online with no faults/fallbacks. The user reported substantially better playback. Reports: `build/fm1/diagnostics-punchout-957.json` and `build/fm1/diagnostics-punchout-957-playing.json`. Display transfers vary with motion because unchanged rows are omitted; the internal 60 fps rate is not the LCD refresh rate. This is a limited game/device trial, not a broad compatibility claim.

MMC1 was subsequently added in FM-1_958. Ninja Gaiden reached Stage 1-1 in a 3,600-frame browser-core smoke test; adaptive/full rendering produced identical audio and presented frames. Its ZIP also passed the exact FM-1 firmware-packing checks and SMK37 cross-compilation. Physical Ninja Gaiden playback has not yet been verified.

The full browser template reserves 393,744 bytes for maximum standard MMC1 plus trainer/header; it is 436,516 application bytes. `npm test` checks NROM/MMC1/MMC2 packing, exact cartridge bytes, unchanged updater and loader, corrupt template rejection, install handoffs, interrupted transfers, active-loader resume, exact restart validation, official restore verification, MIDI discovery and progress accounting. C loader simulations check flash write boundaries and reverse restore. SMK37 remains compile/control-tested with no USB updater enabled.

## Website firmware workflow

The **Install on your FM-1** panel sits beside the browser player (above it on small screens). Its four steps keep the selected game, connection status and final install action visible together.

1. **Choose your game:** drag a `.nes` or `.zip` onto **Drop your game here**, click that same area to choose a file, or select a free homebrew. This is the single cartridge picker for both browser playback and installation. Folder browsing and multi-game ZIP selection stay within this step; choosing a new file clears any previously prepared firmware.
2. **Connect your FM-1:** turn it on and connect it directly to the computer with a USB data cable. Disconnect the recovery adapter, close other MIDI apps and unplug other instruments. Factory M-VAVE V15 is supported. Use Chrome/Edge on HTTPS or localhost and allow MIDI/SysEx access.
3. **Prepare your game:** the browser patches and verifies a pinned template locally. Preparation does not write the device. Saving a `.fwsc` is optional; no download or compiler is needed to install from this page.
4. **Install and play:** the always-visible install button becomes available after preparation. It checks the device again, pauses emulation, locks cartridge changes and requires the expected restart identity before reporting success. Keep power and USB connected. Interrupted transfers offer log export and an explicit retry; no write is retried automatically.

Connection help, transfer details and **Return to the original M-VAVE synth** are expandable below the steps. Restoration verifies the included M-VAVE V15 image. Generic `ota-FM-1` loaders still require physical-model confirmation because some SMK loaders use that identity.

Run `npm run test:ui` with Playwright and Chrome available for isolated desktop/mobile UI checks. `PLAYWRIGHT_MODULE` may point to an existing Playwright module. These tests simulate MIDI and never access a device. The existing `npm run test:site` checks firmware packaging and transport behavior.

The FM-1/SMK-37 Pro/SMK-37 Elite simulator views use the shared key/pad mappings. Click highlighted controls or enlarge the live screen. The classic NES controller remains available. Selecting SMK37 in the firmware deck disables FM-1 build/install/restore operations; it does not claim a validated SMK flasher.

## Remaining hardware work

Improve LCD refresh and broader game/audio compatibility, and validate physical SMK37 installation/recovery before enabling its flasher. More mapper support needs separate compatibility work. The original diagnostic is the included NES cartridge; GameDude's Game Boy homebrew games are not NES-compatible.

Read-only diagnostic SysEx requests use `7D 4E 53 version` (`7D 'N' 'S'`), separate from GameDude. Version 3 appends five uint32 fields to the retained 35-field platform record: last/max/total emulator ticks, measured frame count, and maximum observed LCD completion time. Values use five 7-bit little-endian chunks; timer frequency is 24 MHz. Total ticks wrap at 32 bits. LCD time includes delayed CPU polling and therefore bounds observed completion latency, not exact wire time.

Version 4 retains those 40 fields and appends cumulative CPU, PPU, APU and scan-IRQ ticks. IRQ time overlaps the other measurements. `python tools/diagnose_device.py --samples 4 --interval 2` collects read-only measurements and computes frame rates and per-frame timings.
