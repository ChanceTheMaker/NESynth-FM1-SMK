# NESynth — NES on FM-1 / SMK37

Shared InfoNES core for a local browser player and dual-core FM-1/SMK37 firmware. Supports **NTSC, mapper 0 (NROM), 1 (MMC1), 2 (UxROM), 3 (CNROM), 4 (MMC3), 9 (MMC2) and 11 (Color Dreams), one controller**. Includes From Below, CodeMaster, Diamond Chase, and an original diagnostic generated by `tools/diagnostic.py`. Homebrew licenses and pinned sources are in `web/homebrew/` and the website credits; no commercial ROMs are included.

The prototype fits the existing FM-1 memory map. The website plays NES/ZIP cartridges, browses a user-selected ROM folder, simulates FM-1 and SMK37 controls, adds games to the device library over Bluetooth or USB, and installs or restores FM-1 and SMK-37 Pro/Elite firmware over USB MIDI. **FM-1 picture, controls, both cores, and update/restart have been exercised. Punch-Out reached approximately 60 emulated frames/sec with audio-prioritized adaptive drawing; screen refresh is lower and other games remain experimental. SMK-37 Pro installation and gameplay have been exercised with the owner build. The calibration-free public SMK core and Elite hardware remain unvalidated.**

Live site: **https://chancethemaker.github.io/NESynth-FM1-SMK/**

## Try it

```powershell
python tools/build.py web
python tools/serve.py --port 8816
```

Open <http://127.0.0.1:8816/>. The diagnostic starts silently. Loading a cartridge, pressing a game control, or choosing **Enable sound** starts audio. **Audio on** confirms the browser audio context is running; a suspended context can be enabled again. Move the diamond with arrows/WASD; A changes pitch and B changes background color. Enter/X = A, Space/Z = B, P = Start, Shift = Select. On-screen controls also work. Input taps are held at least 40 ms; focus loss releases all controls.

Drop a `.nes` or `.zip` file onto **Drop your game here** in step 1, or click the same area to choose one. This single picker feeds both the browser player and installer. Load one file at a time. ZIPs containing one `.nes` file open automatically; archives containing several show a cartridge picker. Standard stored and DEFLATE ZIPs are supported, including cartridges in subfolders and uppercase `.NES` extensions. Mac metadata files are ignored. Extraction and checksum validation happen locally; nothing is uploaded. The browser limits archives to 64 MiB and extracted cartridges to 1 MiB, and rejects encrypted, split, ZIP64, damaged, or unsupported-compression archives. DEFLATE extraction requires a browser with `DecompressionStream('deflate-raw')` support.

Legacy `DiskDude!` headers are repaired in memory when imported. The checksum-identified Ms. Pac-Man (Tengen) overdump also has its excess graphics removed and horizontal mirroring restored, using the verified PRG/CHR and board metadata in [MAME](https://github.com/mamedev/mame/blob/master/hash/nes.xml) (`mspacmnt`). Unknown oversized dumps are still rejected; this does not enable NES 2.0 or special consoles. The original NES/ZIP file is never rewritten. The browser player, firmware builder, and Python cartridge reader use the same repair.

Accepted cartridges have a standard iNES 1.0 header. Mapper 0 accepts 16/32 KiB PRG and zero/8 KiB CHR; mapper 9 accepts power-of-two PRG sizes from 32 to 128 KiB and CHR ROM from 8 to 128 KiB. Mapper 1 supports standard MMC1B boards with power-of-two 16?256 KiB PRG, zero/8?128 KiB CHR, and at most 8 KiB PRG RAM. Expanded SxROM RAM/512 KiB PRG boards and MMC1A variants are not supported. An optional 512-byte trainer is supported. NES 2.0, PAL, other mappers, special console variants, and unsupported RAM sizes are rejected before entering the core. ZIP support does not change cartridge compatibility. A valid header does not guarantee accurate gameplay.

Mapper 2 supports standard UxROM with 32–256 KiB PRG and 8 KiB CHR RAM. Mapper 3 supports CNROM with 16/32 KiB PRG and 8/16/32 KiB CHR ROM. Mapper 4 supports standard MMC3 banking with 32–512 KiB PRG, zero/8–256 KiB CHR, four-screen mirroring and PRG-RAM protection. Bank sizes must be powers of two. The browser can load larger MMC3 games than the instrument: device firmware reserves 524,816 bytes (512 KiB plus header and trainer). Oversized device games get a separate error and remain playable in the browser. UxROM/CNROM use conflict-free register writes; MMC3 IRQs are a scanline approximation, with MMC3A/MMC6 and clone-specific behavior unimplemented. These are experimental compatibility limits, not a guarantee for every game.

The browser's default game simulator is a CRT television with a console and playable controller beneath it. The NESynth logo is on its gray enclosure. Instrument simulators match the current NES-order firmware controls. Drag the TV channel readout or upper tuning knob to discover 12 animated demoscene channels (04–15). Channel 03 or Escape returns to the loaded game without replacing it; emulation and its audio stop while a demo is showing. Click the left/right halves of either TV dial to lower/raise its setting; dragging still works. The lower TV volume knob and browser volume slider stay in sync. Fullscreen opens a movable retro clicker with channel and volume buttons, a CH 03 game button, and a close button. Reopen it with TV remote. Channel and volume controls also support arrow keys, Home and End.

## Build and verify

Requires Python 3, Node, and Zig. Instrument compilation uses WSL and the JieLi pi32v2 toolchain. Defaults match the local GameDude setup; override with `ZIG`, `JIELI_TOOLCHAIN`, `--zig`, or `--toolchain`.

```powershell
npm test
python tools/build.py sanitize
python tools/build.py fm1
python tools/build.py smk37
```

`sanitize` requires g++ in WSL. It runs the host suite with AddressSanitizer and UndefinedBehaviorSanitizer. Normal builds use no downloaded packages and do not access any connected device.

Run `npm run firmware` to regenerate the verified browser template (requires the local pinned AC79 SDK and restore fixture configured in `tools/package_fm1.py`). The template contains only our original diagnostic.

Hardware outputs are under `build/fm1/` and `build/smk37/`, with ELF symbols, section reports, manifests, and `nes-NOT-FOR-INSTALL.bin`. These are raw link products, **not `.fwsc` packages**. `tools/package_fm1.py` creates and validates `.fwsc` packages with forward/reverse loader simulations. The experimental source identity is `FM-1_961`. Do not feed raw link binaries to an updater.

`--rom path.nes` or `--rom path.zip` embeds a private cartridge. For a ZIP containing several cartridges, add `--rom-entry "folder/game.nes"`. `--rom-capacity` changes the reserved file slot. Build artifacts are ignored. The default 64 KiB slot accommodates NROM; MMC2 cartridges may need a larger slot (for example, `--rom-capacity 262672`). Enlarging it does not enable more mappers.

## Architecture

- CPU0 owns NES CPU/PPU/APU emulation, controller state, audio interrupts, USB, and LCD DMA.
- Rendering uses a 256-word scratch scanline, then a 61,440-byte indexed frame.
- CPU1 scales an immutable indexed-frame snapshot into a 240×225 RGB565 buffer. The image is centered at LCD y=7; both axes use a 15/16 scale.
- Hardware adaptively rasterizes every third to sixth emulated frame, targeting 10?20 pictures/sec while running CPU/APU and mapper fetches on every frame. Drawing backs off when the audio queue falls below 2,200 samples. The browser rasterizes every frame. CPU1 compares RGB565 rows against the last submitted image; LCD DMA transfers only the changed row range. Duplicate raster frames are not resubmitted. Worker timeout/fault retirement and local scaling fallback are retained, with a full refresh after a fault.
- MMC1/MMC2 decode only fetched tile rows and caches them by immutable CHR-ROM address. The row cache resets when a cartridge resets or loads. Hot CPU, PPU, mapper and scaler code runs from executable SRAM on the instruments.
- The 44.1 kHz mono ring feeds both output channels. Browser audio scheduling drives emulation while sound is active; a monotonic timer drives silent playback. The rational sample count targets approximately 60.0988 NTSC frames/sec.
- The original APU is an approximate linear mix with a DC-blocking filter. No claim of cycle-accurate PPU/APU timing, exact sprite behavior, emphasis-color emulation, or broad NROM compatibility is made.

The retained `gp_*` and some `gb_*` names are the GameDude platform interface, not a second Game Boy core.

The browser downloads that model's pinned official package from the [SMK documentation mirror](https://github.com/jonathaslacerda/smk-37-pro-docs/tree/ab85d7340163ba9e171dc9396e31c034829bbc02/firmware), checks its exact SHA-256, and creates the NESynth package locally. The current page automatically assembles the NESynth library core; the raw application is not sent directly to the device. Updater-enabled Felucca/Sloop/Melodee builds with SMK identity 922 or newer, Doom identity 007 or newer, and NESynth use the portable RAM-loader route. Older firmware without that updater requires adapter migration.

**Return to the original M-VAVE synth** restores the exact selected model's 016 application. The RAM updater checks the supported flash chip, factory boot CRC and per-device calibration before writing. It preflights all sectors, writes only `0x4000..0x9d000`, verifies each sector and preserves boot/calibration. It requires an explicit retry after interruption and an exact restart identity before success. Power loss during programming may require adapter recovery. Generic `ota-FM-1` identity is accepted for Elite only after explicit physical-model confirmation.

SMK-37_962 sends LCD pixel data asynchronously, allowing NES emulation and audio production to continue during DMA. The shared framebuffer remains reserved until completion; a 250 ms transfer timeout disables the display while leaving emulation and USB recovery available. LCD DMA is stopped before entering the RAM updater. CPU1 scaling, adaptive rendering and Fader 1 volume remain enabled. On the owner's Pro running Super Mario Bros. (JU), SMK-37_962 measured 41.96 emulated frames/sec, 88.20 new audio underruns/sec and no CPU1 faults/fallbacks or LCD timeouts. The scanner consumed 33.86% of elapsed CPU time and completed about 12,545 full scans/sec (about 200,718 interrupts/sec). LCD updates were 3.62/sec during this sample; unchanged rows/frames are omitted, so that value depends on scene motion.

SMK-37_963 addresses that measured scanner load by changing only SPI2's scan divider from 5 to 95, before the first transfer. The 16-row latch sequence, ADC settling/completion pipeline, keys, pads and Fader 1 mapping remain intact. Expected full keyboard scan rate is around 1 kHz; actual input responsiveness, analog sweep rate and game speed require a new physical measurement. The vendored scanner now accepts `SMK37_SCAN_BAUD`, retaining its original default of 5; NESynth's local configuration supplies 95. This does not change CPU, audio or LCD clocks.

### Local SMK Pro Bluetooth diagnostic (964)

`python tools/build_bluetooth_probe.py --diagnostic` builds a **separate diagnostic**,
not a game-playing release. `--peripheral` instead measures NESynth plus this GATT
profile with inert hooks. Default invocation remains the original central fit probe.
[Diagnostic evidence](experiments/bluetooth/diagnostic-evidence.json) records the
local build, calibration selection and tests. The public site remains SMK963. The owner's
private candidate passed hardware advertising, connection, an eight-byte RAM
echo with count increment, and re-advertising after disconnect on 2026-10-16.
The controller reached stage 7 with no fatal or allocation errors. Game upload,
longer stability testing and post-radio USB restoration are still pending.

The validated Pro016 flash directory places VM at `0x9d000` with length `0x23000`.
The pinned SDK `cfg_tool.a` caps sector-aligned VM at 128 KiB and divides it into
two banks. The reader uses bank headers at `0x9d000` and `0xad000`, walks records
sequentially, checks every record CRC, and requires RF trim, crystal and PA data.
It refuses ambiguous/transitional banks, malformed records and failed reads;
it never runs SDK VM initialization, defrag or writes. On the owner's paired stock
backup it selects RF record `0x9d015` after validating 14 records. The second
candidate `0xbe015` is outside the SDK-managed range and is not used. This reader
targets the audited SMK Pro layout; it does not claim to handle every VM revision.

The diagnostic starts with CPU1, emulation, audio and Bluetooth inactive. The LCD
shows **PRESS PLAY** and USB restoration is available. A fresh PLAY press starts
the radio using the device's own calibration. Expected subsequent states are
**STARTING**, **ADVERTISING**, then **CONNECTED**. It advertises **NESynth SMK Test**.
The custom service has an eight-byte RAM echo; there are no cartridge writes or
bonding. Startup uses the cooperative app task, actual ICFG interrupt detection,
bounded callback lengths and duplicate-event guards from the reconciled references.
The build verifies RAM code cannot reach XIP and that application flash-writing
routines compile to immediate failure. The separate existing RAM updater retains
its bounded application-write capability for installation/restoration.

```powershell
python tools/build_bluetooth_probe.py --diagnostic
node tools/package_bluetooth_diagnostic.mjs build/smk37/stock-pro.fwsc
python -m pip install --target build/bluetooth-python-deps bleak==3.0.2
# After installing the local diagnostic and pressing PLAY:
python tools/inspect_bluetooth_diagnostic.py  # USB status; no radio start or flash write
python tools/test_bluetooth_diagnostic.py
```

Local outputs are in `build/bluetooth-diagnostic/`: the model-specific
`NESynth-SMK-Pro-964-Bluetooth-Test.fwsc`, its `.smkupdate` RAM-loader packet and
JSON reports. The raw `.bin` is not an installer. The package round-trip verifies
exact application bytes and protected boot; the actual update packet also passes
the C RAM-loader simulation with a synthetic calibration fixture and preserved tail.
No vendor firmware, device calibration or game ROM is committed or published.

Hardware testing on 2026-10-16 found that the owner's live VM region had
already been repurposed by Melodee: `0x9d000` was erased and `0xad000` held
its `MSP2` object header. The default reader correctly reported error 1 before
starting the controller. USB metadata is available through the inspector above;
it contains state, parser/read results and bank markers, never RF payload bytes.

For this case only, `--diagnostic --private-calibration-backups FIRST SECOND`
accepts two identical full stock backups and validates their records with the
same C parser. It embeds only RF/crystal/PA records and the protected 8 KiB
factory region in an ignored local image. Before using the saved records, the
device must match the validated 556-byte `usrtrim` record at `0xc1000` byte for
byte, the same record the SMK updater and Melodee use as the unit fingerprint.
A mismatch or failed read refuses the saved RF data. The surrounding 8 KiB is
compared separately to report changed-sector offsets without exposing bytes. This does not restore or write VM/music storage. Packages are prefixed
`PRIVATE-`; neither the generated header nor firmware may be committed or
published. This fallback is device-specific, available to the diagnostic and SMK965
loader, and is not a calibration migration. When the owner confirms the stock RF backup belongs
to this same unit but its current factory data has changed, two current private
reads can be collected with `tools/backup_bluetooth_factory.py --output-dir
build/bluetooth-diagnostic/live-factory` while the radio is off. Optional
`--private-unit-backups FIRST SECOND` uses that matching pair for the installation
guard while retaining the validated stock RF records as the radio source. The
source relationship must be confirmed by the owner; matching current reads alone
does not prove an old RF backup belongs to that device.

The test client uses [Bleak discovery](https://bleak.readthedocs.io/en/latest/api/scanner.html)
and [GATT reads/writes](https://bleak.readthedocs.io/en/latest/api/client.html), matches
both the diagnostic name and UUID, requires exactly one match, writes a random
eight-byte nonce and checks its echo and counter before disconnecting. Service UUID:
`f86c4cf1-cf8b-4bc4-bc4c-d6f47eabe7e0`; value UUID ends in `e7e1`.

**Power-cycle before USB restoration and leave PLAY untouched.** A USB update
request after Bluetooth starts reboots to radio-off mode; retry the update after
that reboot. This avoids running the RAM updater while controller tasks/IRQs remain
active. The SMK964 diagnostic was physically installed and its radio startup, Bluetooth
connection, RAM echo and re-advertising were verified on this SMK Pro; this
section describes the earlier diagnostic, separate from the integrated SMK965 build above.

Improve LCD refresh and broader game/audio compatibility, and validate physical SMK37 installation, playback and recovery before promoting its experimental installer to a hardware-validated release. More mapper support needs separate compatibility work. The original diagnostic is the included NES cartridge; GameDude's Game Boy homebrew games are not NES-compatible.

Read-only diagnostic SysEx requests use `7D 4E 53 version` (`7D 'N' 'S'`), separate from GameDude. Version 3 appends five uint32 fields to the retained 35-field platform record: last/max/total emulator ticks, measured frame count, and maximum observed LCD completion time. Values use five 7-bit little-endian chunks; timer frequency is 24 MHz. Total ticks wrap at 32 bits. LCD time includes delayed CPU polling and therefore bounds observed completion latency, not exact wire time.

Version 4 retains those 40 fields and appends cumulative CPU, PPU, APU and scan-IRQ ticks. IRQ time overlaps the other measurements. `python tools/diagnose_device.py --samples 4 --interval 2` collects read-only measurements and computes frame rates and per-frame timings.
